# 0.4.0-vehicle-test.10 — runtime rescue and architecture audit

## Disposition

Status: `DEVELOP / VALIDATE`

This candidate exists because physical testing rejected `0.4.0-vehicle-test.9` before Guided workflow validation could begin.

Observed with `.9` in real TunerStudio:

- plugin startup was extremely slow;
- AE Tuner did not receive/display live ECU data;
- the build was not usable enough to begin the planned Guided road test.

`.9` is therefore `REVISE` and must not be tested further.

Accepted release remains `0.3.18` on `main`.

## Root cause 1 — host attachment could close the plugin

`.9` added destructive lifecycle behavior to the nested root tab hierarchy listener:

- when the nested tabs were showing, it adjusted preferred size;
- otherwise, if the lifecycle was active, it called the full close path.

The listener did not require `HierarchyEvent.SHOWING_CHANGED`.

A TunerStudio persistent-dialog plugin can be initialized and then attached/reparented through a hierarchy that is still hidden. Parent/displayability/layout hierarchy changes are normal during that process. In `.9`, any such transition while `rootTabs.isShowing()` was false could therefore invoke full shutdown immediately after successful initialization.

The full shutdown path disconnected `AeTunerPanel`, which owns the sole TunerStudio output-channel subscription. This provides a direct mechanism for the physical symptom: plugin UI eventually appears, but no live ECU values arrive.

### `.10` rule

Host lifecycle and Swing visibility are separate concerns.

- Only `SHOWING_CHANGED` is treated as a visibility event.
- Hidden transitions before the first real display are ignored.
- A post-first-show hide is reversible and cannot destroy the controller subscription.
- Full controller teardown is reserved for the TunerStudio `ApplicationPlugin.close()` callback.

## Root cause 2 — close-time EDT/recovery wait cycle

`.9` could enter the following ordering:

1. hierarchy-triggered close runs on Swing EDT;
2. `GuidedCapturePanel.terminateForClose()` marks recovery dirty;
3. recovery schedules a checkpoint about two seconds later;
4. `EvidenceRecoveryManager.flushAndClose()` submits final work and shuts the executor down;
5. `.9` waits up to 12 seconds for that executor;
6. the already-scheduled dirty task may still start and call `captureSnapshot()`;
7. the recovery worker calls `SwingUtilities.invokeAndWait()` to the EDT;
8. EDT is already waiting for the recovery worker to terminate.

That is an EDT ↔ recovery-worker wait cycle. The 12-second timeout bounds it but does not make startup responsive.

This provides a coherent explanation for the two physical symptoms occurring together: accidental startup shutdown removes live data, then recovery shutdown can make startup appear extremely slow.

### `.10` rule

- Cancel any deferred dirty checkpoint before final recovery shutdown.
- Capture the final model snapshot before shutting the executor down.
- Never make the Swing EDT wait for recovery-worker termination.
- Non-EDT close may use only a short bounded wait.

## Root cause 3 — CI did not exercise the failing host path

The existing `SyntheticPluginIntegrationTest` instantiates the real `AeTunerPlugin`/Swing panel but deliberately does not mock `ControllerAccess`.

Its fixture then injects configuration, project snapshot, channel names and output values directly through reflection. It does not call `ApplicationPlugin.initialize(ControllerAccess)`.

Consequences:

- `.9` `lifecycleActive` never became true in that fixture;
- real TunerStudio output-channel subscription startup was bypassed;
- the hierarchy listener could not reproduce the physical startup self-close;
- component-level lifecycle tests could all pass while the actual host shell remained broken.

### `.10` regression

`RuntimeOverhaulRegressionTest` explicitly models the host-shell state after initialization and verifies:

- non-visibility hierarchy churn while hidden cannot destroy lifecycle;
- pre-first-show hidden `SHOWING_CHANGED` cannot destroy lifecycle;
- post-show hide suspends presentation without destroying host lifecycle;
- reopen restores presentation;
- the default Passive tab does not activate the Guided controller/engine;
- a pending delayed recovery checkpoint cannot make an EDT close approach the old 12-second timeout.

## Startup load audit

### `.9` duplicate project reads

`.9` initialization called:

1. `AeTunerPanel.connectController()` → `reconnect()` → `readProjectData()` → full `AeControllerBridge.readSnapshot()`;
2. `GuidedCapturePanel.connectController()` → `readProjectAxes()` → another full `AeControllerBridge.readSnapshot()`.

The Guided path only needs its project axis before Guided use, yet startup performed the second full ControllerParameter sweep immediately.

### `.10` change

The plugin opens on `Passive capture / reports`.

`.10` therefore:

- initializes the passive TunerStudio subscription first;
- does not connect Guided to `LiveSampleStream` during normal passive startup;
- does not perform the Guided project-axis read during normal passive startup;
- prepares Guided only when the user selects the Guided Capture tab;
- suspends Guided again when another tab is selected.

This removes the duplicate project read from the startup critical path and removes idle adaptive processing from normal passive operation.

## Sample-path coupling audit

The passive sampling path remains an important structural risk:

```text
AeTunerPanel output-channel callback
  -> maybeRecordSample() under samplingLock
  -> SessionMonitor.addSample()
  -> LiveSampleStream.publish()
  -> GuidedCapturePanel.onLiveSample()
  -> AdaptiveGuidedCaptureSession.accept()
  -> drainOutcome()
  -> snapshot()
```

`LiveSampleStream.publish()` is synchronous. Listener exceptions are isolated, but listener latency is not.

In `.9`, Guided subscribed immediately at plugin startup. After the arming delay, every passive sample reached the adaptive session even if no Guided Session was active. `AdaptiveGuidedCaptureSession.accept()` updates its rolling window before returning for IDLE/PAUSED/COMPLETE state, and `GuidedCapturePanel` also requests a session snapshot on each armed sample.

`.10` removes this cost from normal passive startup by keeping Guided disconnected until its tab is active.

A later structural phase should move Guided computation entirely off the passive callback thread or move publication outside the passive sampling lock with explicit queue/drop-health semantics. That is intentionally not combined with the first host-runtime rescue.

## Adaptive engine bloat audit

`AdaptiveGuidedCaptureSession` is approximately 1,294 lines and currently combines too many responsibilities:

- top-level workflow state transitions;
- rolling sample-window ownership;
- trend/regression fitting for RPM/MAP/TPS;
- baseline eligibility and recovery checks;
- opening-pending/local-onset logic;
- pedal plateau detection;
- MAP gap/catch-up measurement;
- gear/VSS observation;
- attempt sample buffering;
- compact trace rendering;
- result/check/instruction string generation;
- valid attempt retention;
- comparability-group coordination.

It also reuses several legacy `GuidedCaptureSession` data types, so `.9` effectively carries a legacy session model and a second adaptive session model at the same time.

`GuidedBlendProposal.Tracker` similarly has two evidence paths: the adaptive `GuidedOutcome` path and a legacy path that parses `Duration:` back out of rendered result text. Model logic parsing its own display text is transitional architecture and should be removed.

## Planned structural split after runtime gate

Preserve semantics while extracting pure responsibilities:

1. `RollingRoadBaselineTracker`
   - bounded rolling window;
   - incremental RPM/MAP/TPS trend/residual statistics;
   - no display text.

2. `GuidedOpeningDetector`
   - drift, opening-pending and confirmed-onset decisions only.

3. `PedalPlateauDetector`
   - natural plateau eligibility/metrics only.

4. `MapCatchupMeasurement`
   - peak gap, catch-up timing and validity only.

5. `AttemptTraceBuffer`
   - bounded raw/compact attempt evidence formatting outside decision logic.

6. `GuidedComparabilityGrouper`
   - evolve current `GuidedRoadGroups` as the sole grouping authority.

7. `AdaptiveGuidedStateMachine`
   - thin coordinator over the components above;
   - owns state transitions but not math/rendering.

8. `GuidedSessionSnapshot`
   - shared immutable data model independent of legacy session implementation.

9. display/report renderers
   - generate strings on UI/report refresh, not on every sample callback.

The legacy compatibility path should be isolated behind an adapter rather than embedded throughout the adaptive model.

Do not begin road Guided Capture yet.

Stationary runtime smoke only:

1. install only the exact `.10` JAR from the validated head;
2. launch TunerStudio and open AE Tuner;
3. verify startup is normal rather than delayed;
4. verify configuration/channel count resolves;
5. verify live RPM, TPS and MAP update normally on Passive capture;
6. open Guided Capture and confirm its axis/live stream activates then;
7. leave Guided Capture and confirm passive data remains normal;
8. hide/close AE Tuner and confirm Guided/audio stops immediately;
9. reopen and verify passive live data returns without duplicate or dead subscriptions;
10. repeat hide/reopen several times;
11. do not paste or approve any proposal.

Only after this runtime gate passes should the adaptive architecture split proceed toward another full Guided road-workflow candidate.
