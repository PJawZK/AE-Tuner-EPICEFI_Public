## Candidate purpose

Earlier Guided Capture vehicle-test candidates proved the UI/audio/capture framework but exposed road-workflow problems:

- a rigid absolute held-TPS target was awkward on-road;
- clean events at changing road load could be rejected by fixed baseline-MAP comparability;
- the final accepted event could be lost at automatic series completion;
- hiding/closing the plugin could leave Guided processing, subscriptions or audio active;
- recovery finalization order could race ongoing capture/audio work.

`.9` addresses those issues without changing the read-only ECU boundary.

## Adaptive Guided Capture behavior

The `.9` workflow uses one adaptive Guided Capture process for road or dyno use. Road/dyno conditions affect event classification/comparability, not the existence of separate user modes.

Key behavior:

- rolling/trend-aware baseline follows reasonable gradual RPM/MAP/TPS load changes before an opening;
- the requested TPS value is a desired **relative step**, not an absolute pedal target;
- a clean natural pedal plateau is measured and retained;
- bounded real pedal movement is tolerated;
- valid events at materially different baseline road loads are retained rather than discarded;
- retained events are automatically separated into comparability groups;
- proposal calculations combine only events from one selected comparable group;
- passive capture remains a background observer rather than a Guided-mode selector.

## Final-event regression

The final comparable event must enter session/evidence/group statistics **before** transition to `SERIES COMPLETE`.

`GuidedVehicleTest9RegressionTest` covers:

- rolling baseline under gradual road-load change;
- natural pedal plateau without an absolute TPS target;
- different-load valid events becoming separate groups rather than exclusions;
- the final event surviving the series-complete transition and increasing the comparable group count before completion.

## Lifecycle/shutdown regression

Closing or hiding the persistent panel must suspend live work immediately.

The candidate lifecycle work covers:

- disconnect Guided processing/shared stream;
- unsubscribe live/passive listeners;
- stop Guided/UI timers;
- cancel current and queued audio;
- prevent intentional cancellation from producing a fallback beep;
- only then finalize recovery evidence;
- allow clean reopen without duplicated listeners or permanently dead timers/audio.

This automated coverage exists because physical `.7/.8` workflow testing showed that state-specific audio could continue after the plugin UI was closed.

Use only the exact candidate JAR identified by SHA-256 above.

### Stationary checks

1. Open the plugin normally.
2. Start/observe Guided state activity as practical.
3. Close the plugin and confirm processing/audio stop immediately.
4. Reopen and confirm one clean live subscription/state pipeline.
5. Confirm automatic recovery discovery/finalization behavior.
6. Exercise Audio Cue Lab and confirm closing the plugin stops current/queued audio without a fallback beep.

### Road Guided Capture

1. Start a fresh adaptive Guided Session.
2. Establish a natural stable road baseline.
3. Make clean pedal openings without trying to hit an exact absolute TPS value.
4. Allow the workflow to retain and group clean events collected under differing road loads.
5. Continue until useful comparable evidence exists or a workflow defect is reproduced.
6. Do not paste or approve a generated proposal during this workflow-validation session.
